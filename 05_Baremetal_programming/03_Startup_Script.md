# Startup File / Code

Let's start by understanding why we need Startup Code.

When we write a program in C, the processor (Cortex-M4) doesn't magically know that the program is in C, nor does it know where the main() function is located. The Cortex-M4 starts executing strictly according to its hardware reset architecture.

The hardware reset mechanism establishes the initial processor state, and the startup code then prepares the C runtime software environment required before our application can safely run. Startup code (commonly an assembly source file like startup_stm32f407xx.s supplied by ST or generated by the toolchain) is essentially the bridge between the processor's hardware reset state and our C application.

Conceptually,
```text
                 HARDWARE WORLD
                       │
                       │ RESET
                       v
              Cortex-M4 processor
                       │
                       │
                       v
                Startup Code
                       │
              ┌────────┼─────────┐
              │        │         │
              v        v         v
             Stack   Memory    Runtime
                     setup      setup
                       │
                       v
                    main()
                       │
                       v
              C application

```
This Startup Code / Startup file is commonly an assembly source file supplied by ST or generated as part of the project. For example, something like `startup_stm32f407xx.s`. The exact filename can vary depending on the toolchain/project. Inside we'll typically find things such as,

-     Vector table
-     Reset_Handler
-     Core Exception handlers(e.g., HardFault_Handler, NMI_Handler)
-     Stack definition
-     Weak interrupt handlers for Peripherals
And sometimes the startup file calls functions responsible for further initialization.

## Phase 1: What Hardware Does Automatically (Silicon Logic)

From our core register fundamentals [M4_Cortex_Core_Registers], we know that R13 is the Stack Pointer (SP), and the Cortex-M4 has two stack pointers: Main Stack Pointer (MSP) and Process Stack Pointer (PSP).

When a reset occurs, silicon logic (hardware) handles initial processor setup before a single line of software code executes. ie, it loads the MSP's initial value and the address of the Reset Handler.(Offset +0x04 -> Reset vector)
```text
0x08000004
     │
     └── address of vector-table entry

[0x08000004]
     │
     v
0x08000101
     │
     └── reset-vector value
```
The reset-vector value normally identifies the reset entry, which in our startup design will be Reset_Handler.
During reset, the Cortex-M4 hardware reads the first two 32-bit entries (8 bytes) from the Vector Table located at Flash address 0x08000000,

```text
Vector Table in Flash
Offset 0x00  (0x08000000) -> Initial MSP value
Offset 0x04  (0x08000004) -> (Reset Vector) because 0x08000004 is the location of the vector-table entry, while the value stored there is the reset vector.
```
```text
            RESET
               │
               v
      Cortex-M4 reset hardware
               │
               │ reads Vector Table entries 0 & 1
               │
        ┌──────┴──────┐
        v             v
   Initial MSP    Reset_Handler address
        │             │
        v             v
     SP (R13)      PC (R15)
```
Key Architectural Detail: Software Does NOT Initialize MSP

The startup software does not execute an instruction like LDR SP, =0x20020000 to set up the stack pointer. The initial MSP setup happens purely as part of the hardware's reset fetch sequence.

When Reset_Handler begins executing, MSP has already been loaded with the top-of-stack address from address 0x08000000

**Why does the Reset Vector address look odd? (e.g., 0x08000101)**

If Reset_Handler is located at 0x08000100, the vector table entry will actually store 0x08000101.
-     This does NOT mean code is at an odd byte address! Code is always 2-byte or 4-byte aligned.
-     Cortex-M4 only executes Thumb instructions.     The least-significant bit (bit 0) acts as the Thumb bit (T-bit).
-     When hardware loads 0x08000101 into the Program Counter (PC), it strips bit 0 to get the real code execution address (0x08000100) while simultaneously setting xPSR.T = 1. If Reset_Handler is located at 0x08000100, the reset vector is
typically represented as 0x08000101. Bit 0 indicates that the target is a Thumb-state address.
The actual instruction address is the aligned address 0x08000100. Cortex-M4 executes Thumb instructions only, so a reset vector with an invalid Thumb-state indication results in a fault/reset problem rather than switching to ARM state.
-     If bit 0 were 0, the processor would attempt ARM mode execution and immediately crash into a UsageFault.
    
## Phase 2: What Software Must Do (Reset_Handler)
Once the hardware sets MSP and loads PC with Reset_Handler, control transfers to software. Why can't startup simply transfer control to main()? Because the RAM state required by normal C execution has not yet
been prepared. In particular, initialized .data objects must contain their initial values and .bss objects must be zero-initialized.
Startup code prepares this required runtime state before calling main().Because before main() executes, the C runtime environment does not exist in memory. Reset_Handler must perform 4 essential software initialization steps,

```text
                    Reset_Handler
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        v                v                v
   1. Stack         2. Copy .data    3. Zero .bss   4. Call SystemInit()
   (Ready via HW)   Flash -> RAM     RAM -> 0       (Optional Clock setup)
                         │                │                │
                         └────────────────┴────────────────┘
                                          │
                                          v
                                       main()
```

```text
                HARDWARE
                   │
                   v
       Read vector table
                   │
          ┌────────┴────────┐
          v                 v
        MSP              Reset entry
          │                 │
          v                 v
       Stack          Reset_Handler
                            │
                            v
                SOFTWARE STARTUP
                            │
                 ┌──────────┼──────────┐
                 v          v          v
               .data      .bss     System init
                 │          │          │
                 └──────────┴──────────┘
                            │
                            v
                          main()
```
**1. The Stack Must Be Ready :**
C functions rely heavily on the stack for passing parameters, holding local variables, and saving registers:
```c
void function(void)
{
    int x = 10; // Local variable allocated on stack
}
```
Because the hardware loaded MSP at reset, the stack is already ready for local variable allocations and function calls.

**2. Initialized Global/Static RAM Variables (.data) Must Be Copied**
Consider an initialized global variable ```c int counter = 10;``` At runtime, counter must live in RAM so its value can change. But when power is off, RAM loses all data. The initial value (10) is saved in non-volatile Flash memory inside the binary image.

Reset_Handler runs a software loop to copy these initial-value bytes from Flash into the .data section in RAM,
```text
Flash
             Program Image
                  │
                  │ Initial value = 10
                  v
             10 stored here
                  │
                  │ Startup copy loop
                  v
                  RAM
             .data section
                  │
                  v
             counter = 10
```
**3. Uninitialized Global/Static Variables (.bss) Must Be Zeroed**
Consider uninitialized variables, 
```c 
int counter;     // Uninitialized global variable
static int flag; // Uninitialized static variable
```
The C language standard guarantees that uninitialized global/static variables start at 0. However, on power-up, RAM contains random electronic garbage.

Because storing thousands of zeros in Flash would waste space, Flash only stores the start and end addresses of .bss. The linker creates symbols representing the start and end of the .bss region. Startup code uses those linker symbols to know which RAM addresses must be cleared. Reset_Handler executes a loop that overwrites that entire RAM region with zeros (0x00).

For example,
```text
RAM

_sbss
  │
  v
┌───────────────────┐
│       .bss        │
│                   │
│ counter           │
│ flag              │
│ ...               │
└───────────────────┘
  │
  v
_ebss
```
The linker gives us _sbss and _ebss; the startup code uses them to perform the zeroing loop.

**4. Early System Configuration (SystemInit())**
Before calling main(), Reset_Handler commonly calls SystemInit(). In STM32 CMSIS-based projects, this configures core clocks (e.g., setting up the PLL to transition from the 16 MHz HSI clock to 168 MHz) and configures flash latency.

Note: Calling SystemInit() is a software convention provided by vendor libraries, not a Cortex-M4 hardware requirement.

Once these steps complete, Reset_Handler branches to main().

### Startup File vs. Linker Script
How does Reset_Handler know where .data begins in Flash, or where .bss starts in RAM? It doesn't hardcode raw addresses. It relies on Linker Script Symbols.
```text
  +--------------------------------------------------------+--------------------------------------------------+ 
  │       Linker Script                                    │    Startup File                                  │ 
  │--------------------------------------------------------│--------------------------------------------------│ 
  │ Mainly Memory & Placement Layout                       │   Mainly Code & Handlers                         │ 
  │--------------------------------------------------------│--------------------------------------------------│      
  │ Linker directives (MEMORY, SECTIONS)                   │   Assembly source code / Weak symbols            │
  │--------------------------------------------------------│--------------------------------------------------│
  │ Defines Flash and RAM physical address bounds          │   Defines Vector Table & Reset_Handler           │
  │--------------------------------------------------------│--------------------------------------------------│ 
  │ Export symbols (_sidata, _sdata, _edata, _sbss, _ebss) │   Executes .data copy & .bss zeroing             │ 
  +--------------------------------------------------------+--------------------------------------------------+
```
```text
            Linker Script
                    │
                    │ Defines layout & symbols
                    v
          Flash / RAM Symbols
     (_sidata, _sdata, _sbss, etc.)
                    │
                    v
              Startup Code
        (Reads symbols to run loops)
                    │
                    v
         Ready .data & .bss in RAM
                    │
                    v
                  main()
```
```text
                                    +-------------------------+
                                    |     VECTOR TABLE        |
                                    | 0x08000000: Initial MSP |
                                    | 0x08000004: Reset_Hdr   |
                                    +-----------+-------------+
                                                |
                         HARDWARE               | Reads entries 0 & 1
                         (Silicon Logic)        v
                                    +-----------------------+
                                    | Set SP (R13) = MSP    |
                                    | Set PC (R15) = Reset  |
                                    +-----------+-----------+
                                                |
                         SOFTWARE               | Executes instructions
                         (startup code)         v
                                    +-----------------------+
                                    | Copy Flash .data      |
                                    | Zero out RAM .bss     |
                                    | Call SystemInit()     |
                                    | Call main()           |
                                    +-----------------------+
```
### Deep Dive: Stack Base Calculation (Top of SRAM)
Let's calculate the exact address placed in Vector Table Entry 0 (Initial MSP) for the STM32F407.

The STM32F407VG has contiguous main SRAM (SRAM1 + SRAM2) starting at base address 0x20000000 with a total size of 128 KB (131,072 bytes).

Note: The chip has 192 KB total RAM, but 64 KB is CCM (Core Coupled Memory) mapped at 0x10000000. The main contiguous SRAM region is 128 KB.

Because ARM Cortex-M stacks are full-descending (the stack pointer points to the last pushed item and grows downward toward lower memory addresses), the initial MSP must point to the very top of SRAM.
Steps:
1.    Convert 128 KB to Bytes (Decimal):   $$128 \times 1024 = 131,072\text{ bytes}$$

2.    Convert 131,072 Bytes to Hexadecimal:

**Method 1: Successive Division:**
Divide the decimal number by 16 repeatedly, keeping track of the remainders. Read the remainders from the bottom to the top to get the final hex value.
```text
131,072 ÷ 16 = 8,192 remainder 0
8,192 ÷ 16 =   512 remainder 0
512 ÷ 16 =    32 remainder 0
32 ÷ 16 =     2 remainder 0
2 ÷ 16 =     0 remainder 2
```
Reading bottom-to-top yields 20000. Adding the 0x radix prefix results in 0x20000.

**Method 2: Positional Powers of 16 **
To find the starting power of 16, look for the largest power of 16 that can fit inside your target number 
131,072: without exceeding it.
```text
131,072 / 65,536 = 2
131,072 = 2 × 65,536
        = 2 × 16⁴
        = 0x20000
        
i.e 
The largest power of 16 that fits into 131,072 is:

16⁴ = 65,536

131,072 ÷ 65,536 = 2

Therefore:

131,072 = 2 × 16⁴
         = 0x20000
```

3. Calculate Top-of-Stack Address (_estack):
Base Address + Size  = Exclusive End Address.
`0x20000000` + `0x20000` = **`0x20020000`**

```text
RAM Layout:

0x20000000 ┌──────────────────────────────────────┐
           │ Bottom of RAM (.data / .bss / Heap)  │
           │                                      │
           │                  │                   │
           │                  v (Grows down)      │
           │               [Stack]                │
0x2001FFFF ├──────────────────────────────────────┤ <- Final usable byte in RAM
0x20020000 └──────────────────────────────────────┘ <- Initial MSP (_estack)
```
-     0x2001FFFF is the final valid byte in SRAM.

-     0x20020000 is the exclusive top-of-stack bound loaded into MSP at reset. When the first item is pushed onto the stack, the processor decrements MSP first (to 0x2001FFFC) and writes the word there.

## The Vector Table Structure
The vector table is a sequential table of 32-bit (4-byte) addresses stored at memory offset 0x00. In the STM32F407, Flash memory is mapped at 0x08000000.
```text
Address        Offset    Contents
────────────────────────────────────────────────────────────────
0x08000000     +0x00     Initial MSP Value (e.g., 0x20020000)
0x08000004     +0x04     Reset_Handler Address (e.g., 0x08000101)
0x08000008     +0x08     NMI_Handler Address
0x0800000C     +0x0C     HardFault_Handler Address
0x08000010     +0x10     MemManage_Handler Address
0x08000014     +0x14     BusFault_Handler Address
0x08000018     +0x18     UsageFault_Handler Address
...            ...       ...
0x080000XX     +0xXX     Peripheral Interrupts (TIM2, USART1, etc.)
```
### Core Exceptions vs. External Interrupts
The vector table contains two types of vectors:

    Cortex-M System Exceptions: Internal CPU events defined by ARM (Reset, NMI, HardFault, SVCall, SysTick).

    Peripheral Interrupts (IRQs): External hardware events defined by ST (TIM2, SPI1, USART1, DMA).

When a peripheral interrupt occurs (for example, TIM2 timer fires):

    Hardware looks up the specific vector offset for TIM2 in the Vector Table.

    Hardware reads the 32-bit function address stored at that location.

    CPU jumps to TIM2_IRQHandler() to service the interrupt.
    
```text
TIM2 Interrupt Fired
         │
         v
Read Vector Table Offset
         │
         v
Fetch TIM2_IRQHandler Address
         │
         v
Execute TIM2_IRQHandler()
```
Summary:
Stage	Triggered By	Key Actions
1. Reset Vector Fetch	Hardware	Silicon loads Initial MSP into R13 and Reset_Handler into PC.
2. C Runtime Prep	Software	Copy .data from Flash to RAM; clear .bss in RAM to zero.
3. Early System Init	Software	Call SystemInit() for clock/PLL setup (optional/CMSIS convention).
4. Application Entry	Software	Transfer execution control to main()
```
