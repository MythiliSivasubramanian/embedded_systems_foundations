# Startup File / Code Explained

Let's start by understanding why we need Startup Code.

When we write a program in C, the processor (Cortex-M4) doesn't magically know that the program is in C, nor does it know where the `main()` function is located. The Cortex-M4 starts executing strictly according to its hardware reset architecture.

The hardware reset mechanism establishes the initial processor state, and the startup code then prepares the C runtime software environment required before our application can safely run. Startup code (commonly an assembly source file like `startup_stm32f407xx.s` supplied by ST or generated by the toolchain) is essentially the bridge between the processor's hardware reset state and our C application.

Conceptually:

```text
                 HARDWARE WORLD
                       │
                       │ RESET
                       v
              Cortex-M4 processor
                       │
                       │
                       v
                Startup Code
                       │
             ┌─────────┼─────────┐
             │         │         │
             v         v         v
           Stack     Memory   Runtime
                     setup     setup
                       │
                       v
                    main()
                       │
                       v
             C application

```

This Startup Code / Startup file is commonly an assembly source file supplied by ST or generated as part of the project (e.g., `startup_stm32f407xx.s`). Inside we'll typically find:

* **Vector Table**
* **Reset_Handler**
* **Core Exception Handlers** (e.g., `HardFault_Handler`, `NMI_Handler`)
* **Stack Definition / Top of Stack Reference**
* **Weak Interrupt Handlers** for Peripherals

## Phase 1: What Hardware Does Automatically (Silicon Logic)

### What Happens at Reset

As soon as power is turned ON or a system reset occurs, silicon logic (hardware) handles initial processor setup **before a single line of software code executes**.

The CPU doesn't discover the vector table by running software. The Cortex-M hardware architecture explicitly defines where the initial vector table is taken from during reset. On the STM32F407, standard boot configuration maps Flash memory at **`0x08000000`**.

During reset, the Cortex-M4 hardware automatically reads the first two 32-bit entries (8 bytes) from the Vector Table located at Flash address `0x08000000`:

```text
| Vector Table Entry | Offset | CPU Loads into | Meaning / Description |
| :--- | :--- | :--- | :--- |
| **Entry 0** | `+0x00` (`0x08000000`) | **MSP (R13)** | Initial Main Stack Pointer value |
| **Entry 1** | `+0x04` (`0x08000004`) | **PC (R15)** | Reset Handler address (Reset Vector) |

```

Conceptually:

```text
               Power-on / RESET
                       │
                       v
        Cortex-M4 hardware reset sequence
                       │
                       v
             Vector table location
                  0x08000000
                       │
             ┌─────────┴─────────┐
             v                   v
        [0x08000000]        [0x08000004]
        Initial MSP        Reset_Handler
           value              address
             │                   │
             v                   v
         SP (R13)            PC (R15)

```

### Key Architectural Detail: Software Does NOT Initialize MSP

The startup software does not execute an instruction like `LDR SP, =0x20020000` to set up the stack pointer. The initial MSP setup happens purely as part of the hardware's reset fetch sequence.

When `Reset_Handler` begins executing, MSP has already been loaded with the top-of-stack address fetched from address `0x08000000`.

### Why does the Reset Vector address look odd? (e.g., 0x08000101)

If `Reset_Handler` is located at `0x08000100`, the vector table entry stored in memory will actually be **`0x08000101`**.

* **Code Alignment:** This does NOT mean code is at an odd byte address! Code is always 2-byte or 4-byte aligned. The actual instruction address is the aligned address `0x08000100`.
* **Thumb State Bit:** Cortex-M4 only executes Thumb instructions. The least-significant bit (bit 0) acts as the Thumb bit ($T$-bit).
* **Execution:** When hardware loads `0x08000101` into the Program Counter (PC), it strips bit 0 to extract the real code execution address (`0x08000100`) while simultaneously setting `xPSR.T = 1`.
* **Why it Matters:** If bit 0 were 0, the processor would attempt ARM mode execution (which Cortex-M does not support) and immediately crash into a `UsageFault`.

```text
0x08000004 (Vector Table Entry location)
     │
     └── Holds value: 0x08000101
                          │
                          ├── Bit 0 = 1 ──> Sets xPSR.T = 1 (Thumb State)
                          └── Bits[31:1] ─> PC = 0x08000100 (Execution Address)

```

## Phase 2: What Software Must Do (Reset_Handler)

Once the hardware sets MSP and loads PC with `Reset_Handler`, control transfers to software.

Why can't startup simply transfer control to `main()` immediately? Because the RAM state required by normal C execution has not yet been prepared. In particular:

1. Initialized `.data` variables must be copied into RAM.
2. Uninitialized `.bss` variables must be zero-initialized.

Before `main()` executes, the C runtime environment does not exist in memory. `Reset_Handler` performs **4 essential software initialization steps**:

```text
                                Reset_Handler
                                      │
         ┌────────────────────────────┼────────────────────────────┐
         │                            │                            │
         v                            v                            v
   1. Stack Ready               2. Copy .data               3. Zero .bss
  (Done by HW)                  Flash -> RAM                RAM -> 0
         │                            │                            │
         └────────────────────────────┴────────────────────────────┘
                                      │
                                      v
                            4. Call SystemInit()
                            (Clock/System Setup)
                                      │
                                      v
                                   main()

```

### 1. The Stack Must Be Ready

C functions rely heavily on the stack for passing parameters, holding local variables, and saving register states:

```c
void function(void)
{
    int x = 10; // Local variable allocated on stack
}

```

Because the hardware loaded MSP automatically at reset, the stack is already fully operational before `Reset_Handler` even runs its first line of code.

### 2. Initialized Global/Static RAM Variables (.data) Must Be Copied

Consider an initialized global variable:

```c
int counter = 10;

```

At runtime, `counter` must live in RAM so its value can change. But when power is off, RAM loses all data. The initial value (`10`) must be saved in non-volatile Flash memory inside the binary image.

`Reset_Handler` runs a software loop to copy these initial-value bytes from Flash into the `.data` section in RAM:

```text
Flash Memory (Program Image)
      │
      └── Initial value = 10
            │
            │ Startup copy loop
            v
RAM (.data section)
      │
      └── counter = 10

```

### 3. Uninitialized Global/Static Variables (.bss) Must Be Zeroed

Consider uninitialized variables:

```c
int counter;     // Uninitialized global variable
static int flag; // Uninitialized static variable

```

The C language standard guarantees that uninitialized global/static variables start at `0`. However, on power-up, RAM contains random electronic garbage.

Because storing thousands of zeros in Flash would waste space, Flash only stores the bounds of `.bss`. The linker creates symbols representing the start (`_sbss`) and end (`_ebss`) of the `.bss` region in RAM. Startup code uses those linker symbols to execute a loop that overwrites that entire RAM region with zeros (`0x00`).

```text
RAM Layout for .bss:

_sbss ──> ┌───────────────────┐
          │      .bss         │
          │                   │
          │  counter = 0      │
          │  flag    = 0      │
          │  ...             │
          └───────────────────┘
_ebss ──>

```

### 4. Early System Configuration (SystemInit())

Before calling `main()`, `Reset_Handler` commonly calls `SystemInit()`. In STM32 CMSIS-based projects, this configures core system clocks (e.g., configuring the PLL to transition from the 16 MHz HSI clock to 168 MHz) and sets Flash latency.

*Note: Calling `SystemInit()` is a software convention provided by vendor libraries, not a Cortex-M4 hardware requirement.*

Once these steps complete, `Reset_Handler` branches to `main()`.

## Phase 3: The Build Process & Deep Dives

### Startup File vs. Linker Script

How does `Reset_Handler` know where `.data` begins in Flash, or where `.bss` starts in RAM? It doesn't hardcode raw addresses. It relies on **Linker Script Symbols**.

| Linker Script | Startup File |
| --- | --- |
| Mainly Memory & Placement Layout | Mainly Code & Handlers |
| Defines memory blocks (`MEMORY`, `SECTIONS`) | Assembly source code / Weak symbols |
| Defines Flash and RAM physical address bounds | Defines Vector Table & `Reset_Handler` |
| Exports symbols (`_sidata`, `_sdata`, `_edata`, `_sbss`, `_ebss`) | Executes `.data` copy & `.bss` zeroing using linker symbols |

```text
Linker Script
     │
     └── Defines layout & exports symbols (_sidata, _sdata, _sbss, _ebss)
           │
           v
Startup Code (Reset_Handler)
     │
     └── Reads symbols to run copy/zero loops
           │
           v
Ready .data & .bss in RAM
     │
     v
  main()

```

---

### Who Writes the Vector Table Entries?

The linker, startup code, and linker script work together to construct the vector table, placing the resulting table directly into the final program image programmed into Flash.

```text
Vector Table in Flash
──────────────────────────────────────────
0x08000000 ──> Initial MSP      (Top of RAM)
0x08000004 ──> Reset Vector     (Address of Reset_Handler + 1)
0x08000008 ──> NMI Vector       (Address of NMI_Handler + 1)
0x0800000C ──> HardFault Vector (Address of HardFault_Handler + 1)
...

```

Here is how the responsibilities are divided:

1. **Hardware Architecture:** Defines the *rules* (e.g., Entry 0 MUST be MSP, Entry 1 MUST be Reset Vector).
2. **Startup Source Code:** Declares the table structure and function names.
3. **Compiler:** Compiles source files into object files (addresses remain unresolved).
4. **Linker Script:** Specifies that the `.isr_vector` section must be placed at address `0x08000000`.
5. **Linker:** Resolves final addresses for `Reset_Handler`, calculates top-of-stack, and writes those exact 32-bit values into the final binary image at `0x08000000`.

```text
       SOURCE CODE
            │
            v
     Reset_Handler()
            │
            v
        Compiler
            │
            v
       Object File (Addresses not final)
            │
            v
         LINKER <─── Linker Script
            │
   ┌────────┴────────┐
   v                 v
Place vector     Place Reset_Handler
table at 0x08000000  code at target address
   │                 │
   └────────┬────────┘
            v
       FINAL IMAGE
            │
            v
      Flash Memory

```

### Deep Dive: Stack Base Calculation (Top of SRAM)

Let's calculate the exact address placed in Vector Table Entry 0 (Initial MSP) for the STM32F407.

The STM32F407VG has contiguous main SRAM (SRAM1 + SRAM2) starting at base address **`0x20000000`** with a total size of **128 KB** (131,072 bytes).

*(Note: The chip has 192 KB total RAM, but 64 KB is Core Coupled Memory (CCM) mapped at `0x10000000`. The main contiguous SRAM region is 128 KB).*

Because ARM Cortex-M stacks are **full-descending** (the stack pointer points to the last pushed item and grows downward toward lower memory addresses), the initial MSP must point to the **exclusive top of SRAM**.

#### Calculation Steps:

1. **Convert 128 KB to Bytes (Decimal):**

$$128 \times 1024 = 131,072\text{ bytes}$$


2. **Convert 131,072 Bytes to Hexadecimal (`0x20000`):**
*Method A: Successive Division*
```text
131,072 ÷ 16 = 8,192  remainder 0
  8,192 ÷ 16 =   512  remainder 0
    512 ÷ 16 =    32  remainder 0
     32 ÷ 16 =     2  remainder 0
      2 ÷ 16 =     0  remainder 2

```


Reading remainders bottom-to-top yields `20000` $\rightarrow$ **`0x20000`**.
*Method B: Positional Powers of 16*
The largest power of 16 that fits into 131,072 is $16^4 = 65,536$.

$$131,072 \div 65,536 = 2$$


$$131,072 = 2 \times 16^4 = 0\text{x}20000$$


3. **Calculate Top-of-Stack Address (`_estack`):**

$$\text{Base Address} + \text{Size} = \text{Exclusive End Address}$$


$$\text{0x20000000} + \text{0x20000} = \mathbf{\text{0x20020000}}$$



```text
RAM Memory Map:

0x20000000 ┌──────────────────────────────────────┐
           │ Bottom of RAM (.data / .bss / Heap)  │
           │                                      │
           │                  │                   │
           │                  v (Grows down)      │
           │               [Stack]                │
0x2001FFFF ├──────────────────────────────────────┤ <- Final usable byte in RAM
0x20020000 └──────────────────────────────────────┘ <- Initial MSP (_estack)

```

* **`0x2001FFFF`**: The final valid, physical byte in SRAM.
* **`0x20020000`**: The exclusive top-of-stack bound loaded into MSP at reset. When the first item is pushed onto the stack, the processor decrements MSP first (to `0x2001FFFC`) and writes the 32-bit word there.

### Vector Table Layout & Peripheral Interrupts

The vector table contains a sequential list of 32-bit addresses. In addition to system exceptions, it maps peripheral interrupts:

```text
Address      Offset   Contents
────────────────────────────────────────────────────────────────
0x08000000   +0x00    Initial MSP Value (e.g., 0x20020000)
0x08000004   +0x04    Reset_Handler Address (e.g., 0x08000101)
0x08000008   +0x08    NMI_Handler Address
0x0800000C   +0x0C    HardFault_Handler Address
0x08000010   +0x10    MemManage_Handler Address
0x08000014   +0x14    BusFault_Handler Address
0x08000018   +0x18    UsageFault_Handler Address
...          ...      ...
0x08000xXX   +0xXX    Peripheral Interrupts (TIM2, USART1, DMA, etc.)

```

The vector table contains two types of vectors:

1. **Cortex-M System Exceptions:** Internal CPU events defined by ARM (Reset, NMI, HardFault, SVCall, SysTick).
2. **Peripheral Interrupts (IRQs):** External hardware events defined by ST (TIM2, SPI1, USART1, DMA).

When a peripheral interrupt occurs (e.g., TIM2 timer fires):

```text
TIM2 Interrupt Fired
         │
         v
Hardware looks up TIM2 vector offset in Vector Table
         │
         v
Hardware fetches 32-bit TIM2_IRQHandler address
         │
         v
CPU jumps to TIM2_IRQHandler() to service the interrupt

```

### Summary Checklist

| Stage | Triggered by | Key Action |
| --- | --- | --- |
| **Reset Vector Fetch** | **Hardware** | Loads initial MSP from `0x08000000` and PC from `0x08000004`. |
| **C Runtime Prep** | **Software** (`Reset_Handler`) | Copies `.data` from Flash to RAM; clears `.bss` to zero. |
| **Early System Init** | **Software** (`SystemInit()`) | Optional system/clock setup (e.g., PLL configuration). |
| **Application Entry** | **Software** | Calls `main()` to begin C program execution. |
